# 大模型 Agent 面试题讲解

## 一、国内 Agent 生态与产品化

### 1）中国内地市面上已经有哪些比较成功的 agent 项目（比如字节的 coze/dify），有什么特点？
以中国内地市场来看，比较有代表性的 Agent 相关项目和平台大致可以分成“面向开发者的构建平台”和“面向业务场景的应用平台”两类，前者里常被提到的包括字节系的 Coze（扣子）这类低门槛工作流+插件生态平台，以及在开发者圈很活跃、可私有化部署且更偏工程化的 Dify；后者则包括百度智能体平台（围绕文心模型和企业工作流集成）、阿里云百炼上的智能体能力、腾讯云与微信生态里的智能体编排能力、科大讯飞星火生态中的行业 Agent 方案等，这些平台成功的共性不是“模型多强”本身，而是把模型能力封装成可运营、可监控、可交付的系统能力，具体表现为：第一，普遍提供可视化编排、知识库接入、工具调用、发布托管、权限控制和日志追踪，降低从原型到上线的门槛；第二，强调与企业现有系统的连接能力，比如 API、数据库、IM、办公套件和工单系统对接；第三，重视稳定性与合规，尤其是内容安全、审计留痕和成本可控；第四，在商业上通常走“平台+生态”路线，通过模板市场、插件市场和行业解决方案形成网络效应，所以真正跑出来的项目往往是“模型能力 + 工程平台化 + 业务闭环”三者同时成立，而不是只做一个聊天入口。

## 二、开发框架与工程体系

### 2）agent 个人项目开发的主流框架有哪些，除了 LangChain?
除了 LangChain 之外，个人开发 Agent 项目的主流路线已经非常多元，按工程风格可以分成几种：一类是工作流/状态机导向框架，例如 LangGraph、LlamaIndex Workflows、Haystack Pipeline 这类更强调可控流程与节点编排的方案；一类是“代码优先、轻框架”路线，比如 PydanticAI、Semantic Kernel、OpenAI Agents SDK（或兼容其模式的社区封装）这类以类型化输入输出、工具注册和会话管理为核心的实践；还有一类是“多智能体协作”导向，如 AutoGen、CrewAI、MetaGPT、OpenHands 一类偏实验和任务协同的框架，适合做角色分工与自动化链式任务；另外，若项目对检索依赖较强，LlamaIndex 本身也常被当作 Agent 架构底座来用，因为它在数据连接器、索引抽象、检索器编排上成熟度较高；如果开发者更关注产品化上线，Dify、Flowise、FastGPT、RAGFlow 这类平台型工具也经常被当成“低代码 Agent 框架”使用；从业界经验看，个人项目选型通常遵循“先可控、再智能”的原则，即优先选观测性好、失败可回放、状态可持久化、依赖少的方案，避免一开始就陷入复杂多 Agent 自博弈框架导致调试困难。

### 3）讲一下 LangChain/LangGraph/LangSmith 等之间的区别和联系
这三者可以理解成同一技术栈里不同层次的能力分工：LangChain 主要负责“应用层抽象”，提供模型调用封装、Prompt 模板、工具集成、检索链路、输出解析等高频组件，适合快速拼装单次调用或线性链式逻辑；LangGraph 则更像“运行时编排层”，它把 Agent 执行过程建模成带状态的图结构（节点、边、条件分支、循环、人工介入点），擅长解决复杂任务中的中断恢复、重试、长流程控制和多步骤决策，因此当业务从 demo 走向生产、需要稳定执行和可恢复性时通常会从纯 LangChain 迁移或叠加 LangGraph；LangSmith 则是“可观测与评测平台层”，用于追踪调用链、记录中间状态、分析失败样本、做数据集评测与回归对比，核心价值在于把“看不见的 Agent 行为”变成可诊断、可优化、可度量的工程资产，所以三者的关系不是替代而是互补，典型落地路径是用 LangChain 组装基本能力、用 LangGraph 管复杂状态机与执行流、再用 LangSmith 做线上调试和离线评测闭环。

## 三、推理范式与工具调用

### 4）讲一下 Function calling 和 ReAct？ReAct 的常见差异化设计是什么？
Function Calling 的本质是“受约束的工具调用接口”，模型根据你声明的函数签名（名称、参数 schema、枚举约束）输出结构化调用意图，再由应用层执行函数并把结果回传给模型，它的优势是稳定、可审计、易治理，适合企业环境；ReAct（Reason + Act）则是“推理与行动交替”的策略，模型在多轮中持续思考、决定是否调用工具、观察结果再更新下一步行动，优势是任务适应性强、面对开放问题更灵活，但也更容易产生长链路误差和成本波动；业界常见的 ReAct 差异化设计主要集中在四个方向：第一是“显式计划化”，先生成计划再执行子任务，减少无效探索；第二是“受限思维与可见中间态分离”，把内部推理压缩为可控摘要，避免泄露冗长思维链同时保留可调试信号；第三是“工具路由策略”，通过规则/小模型先筛选可用工具，降低误调用；第四是“纠错与回退机制”，如超时重试、工具结果校验器、置信度门控和人工接管节点，从工程实践看，生产系统通常不是二选一，而是 Function Calling 作为执行层标准接口，ReAct 作为上层决策策略，两者组合使用最常见。

### 8）Agent skills 是什么，举例？MCP 和 skills 的区别？
Agent skills 可以理解为“可复用的任务能力单元”，它通常不是单一函数，而是一组围绕目标任务封装好的 Prompt、工具编排、输入输出约束、错误处理和质量校验逻辑，例如“网页调研并生成带引用摘要”“读取财报并输出结构化风险要点”“从工单系统拉取数据后生成周报”都可以被封装成 skills，skills 的核心是面向任务语义复用，强调在不同场景中直接调用并保持行为一致；而 MCP 更像“能力接入协议层”，它解决的是模型或 Agent 如何标准化连接外部工具、资源与上下文服务的问题，强调的是互操作和连接方式而非业务能力语义，因此二者关系是上下层关系：skills 负责“做什么、如何保证结果质量”，MCP 负责“通过什么协议接入外部能力”，一个技能可以通过 MCP 调多个外部服务，也可以完全不依赖 MCP；在团队工程实践中，skills 往往沉淀为业务资产库，MCP 则沉淀为基础设施能力，两者搭配后能同时提升复用效率与系统可扩展性。

## 四、会话记忆与 RAG

### 5）多轮对话的主流实现方案？是否需要外部包？
多轮对话的主流实现方案通常是“短期上下文窗口 + 长期记忆存储 + 会话状态管理”三层结构，短期层把最近若干轮消息直接拼接到模型输入，长期层把历史对话摘要、用户画像和关键事实存入数据库（如 Redis/Postgres/向量库），状态层维护线程 ID、工具执行结果和当前任务阶段，并在每轮调用前做上下文裁剪与记忆注入；在工程上常见做法包括滑动窗口、摘要压缩、分层记忆（episodic/semantic/procedural）和检索式记忆回填，以控制 token 成本和避免上下文污染；是否需要外部包取决于目标复杂度，如果只是简单聊天，用原生 SDK + 自己维护消息数组就能实现多轮，不强依赖框架，但一旦涉及工具调用、并发会话、持久化、可回放调试和复杂记忆策略，使用框架或中间件（如 LangGraph、LlamaIndex、Semantic Kernel、Redis 客户端、向量数据库 SDK）会显著降低复杂度并提升可维护性，所以“能不用包”是技术上可行，“不用包更好”在生产环境通常不成立。

### 6）搭建 RAG 系统的流程？常见 RAG 使用的数据库有什么？RAG 检索优化策略有什么？如何评估搭建的 RAG 系统？
搭建 RAG 的标准流程一般是先做数据接入与清洗（去重、结构化、权限标签化），再进行分块与元数据设计（chunk 大小、重叠策略、来源字段、时间与权限字段），随后生成向量并写入索引（必要时同时建立关键词倒排索引），在线阶段执行“查询理解/改写 → 检索召回 → 重排过滤 → 上下文构建 → 生成回答 → 引用回传”，并在链路中加入缓存、权限校验和监控；常见数据库组合是“向量库 + 结构化库 + 缓存”三件套，其中向量库常见有 Qdrant、Milvus、Weaviate、Pinecone、pgvector（PostgreSQL 扩展）以及 Elasticsearch/OpenSearch 的向量能力，结构化库常用 PostgreSQL/MySQL 存文档元信息和权限，缓存层常见 Redis；检索优化策略主要包括混合检索（BM25+向量）、多路召回（按实体/时间/文档类型拆路）、查询重写与扩展、Cross-Encoder 重排、父子块检索、上下文去冗余、基于反馈的 hard negative 持续训练以及按业务场景设定“宁可拒答也不胡答”的阈值策略；评估上需要离线与在线结合，离线看召回率、MRR、NDCG、上下文命中率、答案正确率和引用准确率，在线看首 token 延迟、完整响应时延、用户采纳率、追问率、人工纠错率和每次请求成本，同时建立失败样本集做持续回归，真正成熟的 RAG 评估不是只看一个正确率，而是把“检索质量、生成可信度、时延成本、业务效果”作为统一指标体系。

## 五、协议标准与多 Agent 互联

### 7）MCP 协议的核心内容？MCP 的通信方式？为什么有些特定推理模型因技术原因不支持 MCP？
MCP（Model Context Protocol）的核心思想是把“模型可访问的外部能力”标准化为统一协议接口，主要围绕资源（Resources）、工具（Tools）、提示模板/上下文（Prompts）以及能力发现、权限边界、调用生命周期管理等机制展开，让不同模型客户端能以一致方式接入外部系统；在通信方式上，MCP 常见实现形态包括本地进程间通信（如 stdio 方式，适合本地工具与插件）、基于 HTTP 的远程服务通信（便于服务化部署）以及事件流式返回（如 SSE 语义）来支持长任务反馈，不同实现会在传输层做取舍但都强调协议层语义一致；至于为什么有些推理模型“不支持 MCP”，多数并不是模型能力本身不能用，而是其所在平台或推理服务在接口层没有暴露与 MCP 对齐的工具调用/会话控制能力，或者缺少稳定的结构化输出约束、双向流式工具调用、权限隔离与沙箱机制，导致很难满足 MCP 所需的完整交互语义，因此现实里常通过“适配层”把模型原生 API 映射到 MCP，而不是要求模型内核天然理解 MCP。

### 9）A2A 协议是什么？A2A 与 MCP 的区别是什么？
A2A（Agent-to-Agent）通常指面向“智能体之间协作”的交互协议或设计范式，核心关注点是多个 Agent 如何声明身份与能力、如何协商任务、如何传递中间结果、如何处理冲突与回退以及如何进行跨 Agent 的状态同步，本质上解决的是“多 Agent 协作网络”的问题；MCP 则主要解决“单个 Agent/模型如何标准化接入外部工具与上下文资源”的问题，本质上是模型到工具（Model-to-Tool/Context）的连接协议，因此两者最关键的差异在交互对象和系统边界：A2A 面向 Agent 与 Agent 的编排协作，强调协商和协同执行；MCP 面向 Agent 与工具/资源服务的能力调用，强调互操作与统一接入；在实际架构里二者并不冲突，常见组合是每个 Agent 内部通过 MCP 获取外部能力，而 Agent 之间通过 A2A（或自定义协作总线）分工协作，前者解决“怎么接能力”，后者解决“怎么协作完成复杂任务”。

## 六、系统工程、Prompt 与稳定性

### 1）SSE 是什么？SSE 有什么局限性？
SSE（Server-Sent Events）是一种基于 HTTP 的单向流式推送机制，服务端可以持续把文本事件推送给浏览器或客户端，典型场景就是大模型逐 token 输出时把中间内容实时返回前端，它的优点是实现简单、天然兼容 HTTP 基础设施、自动重连语义清晰、对“服务端持续输出、客户端只消费”的场景非常友好；但 SSE 也有明显局限：第一是单向通信，客户端无法通过同一连接反向发消息，双向交互要配合额外请求或改用 WebSocket；第二是对中间网络设备较敏感，反向代理、网关、CDN 若配置不当会缓冲流或超时断开；第三是连接数规模化时需要谨慎设计资源管理，因为每个长连接都会占用服务端并发资源；第四是二进制与复杂多路复用能力弱，消息格式通常是文本行协议，不如 WebSocket 灵活；第五是移动网络环境下重连抖动更明显，因此生产实践一般会给 SSE 增加心跳、断线续传游标、幂等事件 ID、网关禁缓冲配置和超时回退策略，确保“流式体验”和“系统稳定性”之间平衡。

### 2）如何写出好的 prompt？如何评估写的 prompt？给出一个 prompt 的设计实例
好的 Prompt 在工程上不是“写得文采好”，而是“目标清晰、边界明确、输出可判定、失败可回退”，通常遵循角色定义、任务目标、输入上下文、约束条件、输出格式、拒答策略、示例（few-shot）和自检规则这几层结构，其中最关键的是把成功标准显式写进提示词并让模型在不满足条件时明确拒答或返回空结果；评估 Prompt 也不能只靠主观阅读，通常要做离线样本集评测（准确率、格式合规率、事实性、引用命中率）、线上 A/B（采纳率、追问率、人工修正率）、鲁棒性测试（对抗输入、缺字段输入、超长输入）和成本时延评估，然后按失败类型迭代；一个可落地的实例是“合同风险抽取 Prompt”，可用段内伪代码框架表达为：`SYSTEM: 你是法务助手，只能依据给定合同文本抽取风险；TASK: 输出付款条款、违约责任、解约条件三类风险；CONSTRAINT: 不得编造，证据不足返回unknown；OUTPUT_JSON_SCHEMA: {risk_items:[{type,clause_quote,reason,severity,suggestion}]}; SELF_CHECK: 校验每个risk_items必须有clause_quote且能在原文定位`，这样的设计能把“能力要求”转成“机器可校验要求”，从而显著提升可控性。

### 3）讲一下模型预热机制是什么？
模型预热机制本质是让系统在真实流量到来前完成“冷启动成本”的前置消化，避免首请求因为模型加载、权重映射、内存页调入、编译优化、KV cache 初始化、连接池建立而出现高延迟甚至超时，常见做法包括服务启动后执行固定 warmup 请求、按租户或热点路由做定时保活、在弹性扩容时先把新副本预热到可服务状态再摘流、对不同模型规格维护分级预热策略（大模型深预热、小模型浅预热），以及在网关层引入预热探针与 readiness gate；在推理平台里还会结合批处理器和缓存策略，例如预创建 tokenizer、预编译图、预加载常用 Prompt 前缀到前缀缓存，降低首 token 时延波动，工程上要注意预热并非越重越好，因为过度预热会浪费算力并抬高空载成本，因此最佳实践是基于业务时段流量画像动态调节预热强度，追求 P95 延迟与成本之间的最优点。

### 4）如何提升 agent 的 function call 能力？
提升 Agent Function Call 能力的核心是把“模型猜测调用”变成“可学习的调用决策系统”，第一步是工具接口设计要语义清晰且参数 schema 严格（字段类型、必填项、枚举、范围约束、默认值、示例齐全），第二步是在 Prompt 中加入工具选择规则与反例，明确什么情况下不能调用工具，第三步是引入调用前后校验器（pre-check 验参、post-check 验结果完整性），第四步是构建调用轨迹数据集做持续优化（统计误调用率、漏调用率、参数错误率、重试率），第五步是做工具路由分层（先轻量分类器决定工具族，再由主模型填参数），第六步是把失败场景做可恢复策略（重试、参数修复、回退到人工或纯文本回答）；如果用伪代码框架表示可以是 `decide_tool(query)->candidate_tools; build_args(schema,context)->args; validate_args(args)->ok?; call_tool(); validate_result(); if fail then repair_or_fallback()`，业界经验显示最有效的往往不是“换更大模型”，而是“更严谨的工具契约 + 更系统的失败闭环”。

### 5）上下文工程是怎么做的？长短期记忆怎么做？
上下文工程的目标是把“与当前问题最相关、最可信、最少噪音”的信息送进模型窗口，典型做法是把上下文分为系统约束层（角色、规则、输出格式）、任务层（当前目标与步骤）、会话层（最近几轮交互）和知识层（检索到的外部证据），在每次推理前执行组装与裁剪；长短期记忆通常采用双存储：短期记忆放在会话窗口内（最近 N 轮+当前任务状态），长期记忆存数据库并按需检索注入（用户偏好、历史事实、已完成任务摘要），同时用“写入门控”避免把低质量内容永久化，常见门控信号包括置信度、用户确认、重复出现频次和任务完成状态；工程上还会通过记忆摘要滚动、冲突检测、时间衰减、权限隔离和主题分桶来防止记忆库膨胀与污染，如果用简化伪代码表示可写成 `short_ctx = last_k_turns + active_task_state; long_ctx = retrieve(memory_store, query, user_id, topic); final_ctx = compose(system_rules, short_ctx, rerank(long_ctx));`，这套方法本质上是在做“上下文预算管理”。

### 6）记忆覆盖的问题如何解决？
记忆覆盖本质是新信息与旧信息冲突或高频噪音把关键信息挤出有效上下文导致行为漂移，解决思路不是简单“记更多”，而是建立版本化、优先级和冲突仲裁机制：对同一事实维护时间戳与来源置信度，采用“新鲜度×可信度×业务优先级”综合评分决定是否覆盖；对关键事实（如用户硬性偏好、合规约束）设为不可直接覆盖的 pinned memory，只能在满足明确条件时变更；对易变事实采用时间衰减和自动失效 TTL；在检索注入阶段加入去重与冲突检测，发现矛盾时让模型先输出“冲突说明+澄清问题”而不是强行回答；实践中还会引入 event-sourcing 思路保留记忆变更日志，使系统可以回放、回滚和审计，因此稳定的记忆系统更像“可追溯知识账本”而不是一个不断覆盖的键值表。

### 7）数据的输入输出格式如何保证大模型输出稳定的 json，你的项目里面做了什么工作？
要保证模型稳定输出 JSON，关键是“多层约束 + 失败重试 + 解析兜底”，输入侧先做结构化预处理（字段标准化、非法字符清洗、长度与类型校验），提示词层明确给出 JSON Schema 与严格规则（仅输出 JSON、禁止解释文本、字段缺失用 null 或 unknown），模型调用层尽量使用原生结构化输出能力或 function calling，输出侧先做 fast parse 再做 schema validate，失败时走自动修复链路（例如基于错误信息二次提示“只修复括号/引号/字段类型”）并限制重试次数，同时对关键字段做业务校验防止“格式对了但语义错了”；结合你这个项目的工程特点，常见做法会落在 `llm_service` 层增加统一响应契约、在 `validation` 配置里维护规则与预算阈值、在工作流执行中记录每次解析失败原因并上报指标，形成“提示词约束—解析校验—异常回退—可观测分析”的闭环，这样才能把 JSON 稳定性从“偶尔成功”提升到“可运营可维护”。

### 8）主流大模型如 llama/qwen 等有哪些区别？
Llama、Qwen 这类主流模型的差异通常不该只看参数规模，而要从训练语料覆盖、中文能力、指令遵循、工具调用对齐、多语言表现、上下文长度、推理效率、开源许可与生态成熟度综合判断，一般来说 Qwen 系列在中文理解与中文指令场景往往更有优势，且在国内工程生态和部署实践中资料丰富；Llama 系列的全球开源生态非常强，社区微调、量化、推理后端适配和论文复现资源多，跨语言社区支持广；在 function calling 与 Agent 任务上，两者都能做但具体表现高度依赖对应版本的指令对齐和工具数据训练，实际选型应基于你自己的任务基准测试而非泛化口碑，建议用同一评测集比较格式遵循率、工具调用成功率、幻觉率、时延吞吐和成本，再结合合规与部署约束决策，最务实的方案通常是“主模型 + 备选模型 + 场景路由”，而不是押注单一模型覆盖全部任务。

### 9）多 agent/多异步场景下，你是如何防止上下文污染的？
在多 Agent 与多异步并发场景里，上下文污染通常来自会话隔离不彻底、状态共享粒度过粗和异步回写乱序，所以治理重点是“强隔离 + 可追踪 + 幂等化”：每个任务必须绑定唯一的 `tenant_id/user_id/thread_id/run_id/agent_id` 复合上下文键，内存与缓存按键分区并设置 TTL，跨 Agent 共享信息只通过显式白名单字段传递而不是直接共享整段历史；异步回调必须携带版本号或事件序号，写入前做 compare-and-swap 防止旧结果覆盖新状态；工具输出进入公共上下文前要做清洗与脱敏，避免把噪声日志或高风险内容注入后续推理；另外要把系统提示、任务提示和检索证据分层存放，生成时按层拼接并打来源标签，出现异常可快速定位污染源；如果用简化框架表达可写成 `state_key = hash(tenant, user, thread, run, agent); load_state(state_key); apply_event(event_id, version) if version_is_new; append_context(layered_context, source_tagged);`，这套机制能在高并发协作下显著降低串话和状态错写。

## 七、实战方案设计与落地

### 1）跨模块错误追踪的 agent 知识库解决方案
跨模块错误追踪在 Agent 系统里难点不在“报错能不能看见”，而在“能不能把一次失败从用户输入一路追到具体模块、具体调用、具体上下文并沉淀为可复用知识”，可落地方案通常是“统一追踪上下文 + 结构化日志事件 + 错误知识库 + 自动归因与修复建议”四层架构：首先在入口网关为每次请求生成全局 trace_id 与 run_id，并把 tenant、thread、agent、workflow_node、tool_call_id 等关键键值强制透传到 llm_service、orchestration、storage、retrieval、tool_calling 全链路；其次定义统一错误事件模型（error_code、module、stack、input_hash、retrieval_hits、model_name、prompt_version、latency、cost、retry_count、severity），所有模块以同一 schema 上报，避免后期无法聚合；然后构建“错误知识库”而不是只存日志，即把原始错误、上下文快照、根因标签、修复动作、回归结果写入可检索存储（结构化库 + 向量索引），支持相似错误召回与推荐处置；再向上加一层自动归因流程，利用规则优先（例如 JSON 解析失败、工具参数缺失、检索为空、超时重试耗尽）+ LLM 辅助归类（从跨模块事件序列里总结根因）生成可执行建议（如回滚 prompt 版本、加 schema 校验、降低并发、调整超时阈值）；线上运维时配合错误预算与 SLO 告警，将高频错误自动升级为“工程任务卡”，并把修复后验证数据回写知识库形成闭环，最终实现“发现问题—定位根因—复用修复经验—防止同类再发”的持续改进体系，这比传统只看单点日志的方式在多 Agent 复杂链路中可靠得多。

### 2）多 agent 执行策略的智能选择和切换机制设计
多 Agent 执行策略真正有效的设计不是固定一个调度图，而是构建“任务画像驱动的策略路由 + 运行时健康感知切换 + 可回退的状态机控制”，具体可以把策略抽象成三类：串行专家链（适合强依赖步骤）、并行专家团（适合信息汇聚）、分层监督型（一个 Planner + 多个 Worker + 一个 Critic），请求进来后先做任务画像（复杂度、时延预算、可靠性要求、工具依赖、历史成功模式）得到策略初选，再根据实时信号（队列长度、模型可用性、工具健康度、成本配额）动态修正；执行过程中必须有状态机守护，例如 INIT→PLAN→EXECUTE→VERIFY→FINALIZE，每个阶段定义超时、重试和降级动作，当监控到失败模式（连续工具失败、质量评分低于阈值、关键节点超时）时触发策略切换，比如从并行协作切到串行保守流程，或从高成本大模型切到中模型+规则兜底；为了防止切换导致上下文断裂，需要使用统一工作记忆对象（任务目标、已完成子任务、证据集、决策日志）作为策略间共享状态，并引入版本化 checkpoint 让任意切换都可回滚；评估上不仅看最终准确率，还要看策略切换成功率、切换后恢复时延、额外 token 成本、失败逃逸率，工程里常把该能力做成 policy engine（规则+学习混合），先靠规则保证可控，再逐步加入 bandit/RL 进行策略优选，这样能在不同任务分布下持续逼近最优执行路径而不是“一套流程打天下”。

### 3）简历关键词提取的技术实现
简历关键词提取如果要达到企业可用标准，通常采用“版面解析 + 语义抽取 + 术语标准化 + 置信融合 + 人机校正”流水线，而不是单纯让模型从整段文本里直接列词，第一步要处理多格式输入（PDF/Word/图片）并做版面结构恢复，识别基本块如个人信息、教育、工作经历、项目经历、技能证书，避免字段串位；第二步做实体与关系抽取，关键词不只包含技能名词，还应覆盖岗位角色、行业领域、项目职责、技术深度、产出指标（如“将响应时延降低 35%”）等可用于匹配的信号；第三步进行术语标准化与同义归并，例如“PyTorch/Pytorch”“LLM Agent/智能体开发”“RAG/检索增强生成”映射到统一本体，同时把过泛词（负责、参与、沟通）降权；第四步用多策略融合提升稳健性，规则词典保证召回，统计特征或轻量分类器做初筛，LLM 负责语义补全与上下文判别，最后按置信度融合排序；第五步输出结构化结果（keyword、category、evidence_span、level、confidence）并保留原文证据片段，支持后续审计与反馈修正；上线后要做行业词库增量维护与主动学习，把招聘方“常点击、常过滤、常面试通过”的反馈回流更新权重，这样关键词系统才能从静态抽取进化为“可优化的匹配引擎”，在实际招聘场景里明显优于一次性抽词。

### 4）长文本生成的技术方案
长文本生成的核心挑战是“长程一致性、事实稳定性、结构完整性、成本时延可控”同时成立，因此可靠方案通常采用“先规划后生成、分段写作、分层记忆、阶段校验”的生产线：先由规划器生成文档蓝图（目标读者、章节树、每章关键论点、证据来源、风格约束），再按章节或段落批次生成，每次生成前注入该章节目标与全局摘要、术语表、禁忌清单，生成后立即做局部校验（事实引用、术语一致、语气一致、重复率），通过后再进入下一段；为避免前后矛盾，需要维护文档状态仓（global summary、entity table、timeline、claims registry），每次新内容产生后更新状态仓并用于后续约束；在超长任务中常用“滑动窗口 + 压缩摘要 + 关键事实锁定”机制，即只把必要上下文放入窗口，把历史内容压缩为结构化记忆，同时把关键事实以不可改写条目固定；如果业务要求高可信度，还要引入检索增强和引用回填，让每个关键结论绑定出处并在最终合稿阶段做一致性复核与反事实检查；工程上可以用异步队列并行生成可独立章节，再由合稿器做风格统一和冲突消解，最终得到既长又稳的文本输出，而不是一次性长上下文直出导致后段漂移和逻辑崩塌。

### 5）复杂任务执行准确率提升的评估方法
复杂任务准确率提升首先要解决“准确率到底是什么”的定义问题，单一 final answer 正误不足以指导优化，建议采用分层评估框架：任务层看最终目标达成率与用户可用率，流程层看子任务完成率、工具调用成功率、关键路径失败率，证据层看检索命中率与引用正确率，格式层看结构化输出合规率，鲁棒层看异常输入与边界条件通过率；数据集构建上要覆盖真实难样本而非只做干净样本，特别要纳入跨工具依赖、长链路决策、歧义指令、信息缺失、权限受限等高风险情形，并通过 failure taxonomy 给每次失败打根因标签（规划错误、检索错误、调用错误、推理错误、执行错误）；方法上采用“离线回放评测 + 在线灰度 A/B + 人工审查”的三段式，离线保证迭代速度，在线验证真实收益，人工用于高风险案例裁决；为了真正提升准确率，评估系统要能反向驱动训练与工程改造，例如发现规划阶段错误占比高就加强计划模板与分解器，发现工具参数错误高就强化 schema 与参数修复器，发现事实幻觉高就提高证据门槛与拒答策略；最终以北极星指标（如复杂任务一次成功率）配合成本时延约束做多目标优化，才能避免“准确率提升但代价不可接受”的伪优化。

### 6）企业内部知识库 RAG 知识动态更新方案
企业 RAG 动态更新的关键不是“能更新”，而是“更新后可控、可追溯、不中断服务”，常见落地是构建 CDC 驱动的增量管道：从文档系统、工单系统、Wiki、代码仓、数据库变更流抓取更新事件，进入统一 ingestion 队列后做解析、去重、权限打标、版本比对，再执行增量切分与向量重建，最后原子切换索引分片；为了保证在线稳定，通常采用双索引或蓝绿索引策略，新索引构建完成并通过抽样评测后再切换查询流量，失败可秒级回滚；更新策略可按文档类型分级，核心制度文档走准实时更新，普通知识走批处理窗口，历史资料低频重建；同时要处理“删除与失效”问题，不能只增不减，需维护墓碑标记与过期策略，确保已废弃知识不会继续被召回；权限一致性也是企业场景核心，检索阶段必须做用户上下文过滤，防止跨部门信息泄露；运维层面配置 freshness、coverage、staleness、index lag 等指标并设置阈值告警，一旦发现更新滞后或召回质量下降立即触发重建或回滚；这套方案本质是把 RAG 索引当成可发布的数据产品来运营，而不是一次性离线构建产物。

### 7）多阶段召回策略优化
多阶段召回优化的核心思想是把“高召回”和“高精度”分层实现：第一阶段做低成本广覆盖召回（关键词 BM25、向量 ANN、多路 query rewrite），目标是尽量不漏；第二阶段做中成本重排（cross-encoder、特征打分、业务规则），目标是压噪；第三阶段做高价值精筛（多样性约束、去冗余、证据完整性检查、权限与时效过滤），目标是把真正可用证据送入生成模型，避免“垃圾进垃圾出”；在策略上可按查询类型自适应路由，例如事实问答偏重精确匹配，分析类问题偏重语义覆盖，时效问题增加时间衰减权重；参数优化不应凭感觉，而要通过离线标注集做网格或贝叶斯搜索，调优 top_k、召回权重、重排阈值、去重阈值等关键参数，并在线监控 answer acceptance 与 follow-up rate 验证真实收益；另外建议引入失败反哺机制，把用户追问、人工改写、拒答样本回流到 query rewrite 与负样本训练中，持续降低“召回到了但没用”与“该召回却漏掉”的比例，最终形成可迭代的多阶段检索系统，而不是一次调参后长期不动的静态流水线。

## 八、项目专项深挖（架构细节）

### 1）Refine 阶段，传入传出的数据格式是什么？如何先通过模型做语义规范化，失败时再规则兜底？
在 Refine 阶段，输入通常是编排层传给 LLM Service 的“原始用户问题 + 运行上下文”的结构化请求，核心字段至少包括用户原始 query、strategy（quick/standard/deep）、可能的领域提示和线程上下文，输出则是一个可用于后续拆解与调度的规范化对象，你项目里实际落到状态上的关键字段是 `normalized_question`、`query_type`、`research_areas`、`complexity` 这类语义标签，本质上是把自由文本转成可调度元数据；语义规范化主路径是调用 `/agent/refine` 让模型执行意图归一化、术语消歧、范围收敛和任务边界补全，然后由编排层进行结构校验并写入 `ResearchState.refined`，如果模型输出不符合预期（例如字段缺失、JSON 不可解析、语义过泛），常见做法是轻量重试或降温重采样，而你这套架构里的兜底思路是规则化回退，即通过正则、关键词词典、启发式模板直接推断 `query_type` 与领域标签并回填 `normalized_question`，保证后续 Decompose 至少拿到可消费输入而不阻断主流程。

### 2）Decompose 阶段多层回退怎么实现？三级升级机制是什么？
Decompose 的多层回退本质是“先尽量让 LLM 产出高质量任务契约，再逐级降低智能依赖保证可执行性”，你的主路径是 `/agent/decompose` 生成任务列表并映射为 `TaskContract`，如果解析失败或任务不合法就触发三级升级机制 `_decompose_tier_sequence`，即先 `small` 再 `medium` 再 `large`，只有当前 tier 的结构化结果不通过校验才升级到下一档，从而在成本和成功率之间做平衡；若升级后依旧失败，则进入规则分解 `_build_rule_based_decompose_tasks`，按问题结构和常见研究流程生成基础任务；若规则分解仍为空，再退到 `_default_tasks` 给出模板化任务骨架；此外编排层还有 `_build_fallback_decompose_tasks` 的本地兜底，形成服务侧与编排侧双保险，这条链路是很典型的工程解法，因为它把“模型能力不稳定”转换成“确定性降级路径”，目标不是每次都最优，而是每次都可运行、可恢复、可追踪。

### 3）Decompose 阶段任务 DAG 如何定义？图方法调用了什么库、用了什么参数？
Decompose 阶段的任务 DAG 定义是“节点=任务、边=依赖关系”，每个任务通过 `deps` 指定前置任务 ID，编排层把任务集转换为 `dependency_count`（入度计数）、`reverse_dependencies`（反向邻接索引）和 `ready_queue`（当前可执行集合），这就是标准有向无环任务图在运行态的表达；从你项目结构看，工作流编排虽然使用 LangGraph，但任务 DAG 本身并不是交给图数据库或 networkx 求解，而是在 `graph.py` 中使用原生 Python 容器（`dict/list/set/deque`）构建并维护，这样做的优势是依赖少、可控性强、易于把业务规则（依赖降级、失败传播、并发上限）直接嵌入调度逻辑；因此关键参数更多是业务调度参数而不是图算法库参数，比如 `max_concurrency`、`max_tasks`、`deps` 完整性校验规则，以及当首轮并发不足时触发 `_downgrade_dependencies_for_parallel` 的策略阈值，这些参数决定的是“系统吞吐与稳定性的工程上限”。

### 4）拓扑排序是怎么设计的？
你这个项目的拓扑排序本质是 Kahn 算法的在线增量版本：初始化时统计所有任务入度，把入度为 0 的任务放进 `ready_queue`，每当某个任务在 Verify 阶段成功或进入终态，就遍历它的 `reverse_dependencies`，将下游任务入度减一，减到 0 就入队等待 Schedule 拉取，所以它不是一次性算出全序列，而是“执行驱动的动态拓扑推进”；这种设计特别适合长链路 Agent 任务，因为调度、执行、验证本身是循环过程，你需要在运行中处理重试、跳过、失败传播和死锁检测，项目里的“无 ready task 但仍有非终态任务”就是拓扑停滞的工程化判定条件；业界在多 Agent 编排里基本也是同一路线，只是在规模更大时会叠加优先级队列、关键路径加权、失败重路由和任务租约机制，以提升高并发下的稳定吞吐。

### 5）Schedule 阶段 ready_queue 怎么设计？是否需要 Redis 队列，为什么？
Schedule 阶段的 `ready_queue` 设计是以内存状态为核心：从当前 LangGraph 状态中筛选“依赖满足且尚未运行”的任务集合，再按 `max_concurrency` 批量分配到 `active_task_ids`，执行完成后由 Verify 回写状态并解锁下一批任务，这本质上是工作流内局部队列而不是跨服务全局消息队列，因此在当前单编排实例持有状态机闭环的架构下并不强制需要 Redis；不用 Redis 的核心原因是你已经通过 checkpoint/状态持久化保证了恢复能力，额外引入外部消息队列会显著增加幂等、去重、可见性超时、一致性对账等复杂度，而短期收益有限；但如果后续目标是多编排器实例抢占任务、跨进程弹性扩缩容、超长任务解耦执行，那么业界常见升级路径就是把 ready queue 外部化到 Redis Streams、RabbitMQ 或 Kafka，并配套任务租约和幂等键，这时 Redis 会从“可选优化”变成“分布式调度必要组件”。

### 6）如何理解“设计依赖降级策略，缓解首轮仅单任务可执行的吞吐瓶颈”？
这句话的核心含义是：当任务 DAG 依赖关系定义过于保守，导致首轮 `ready_queue` 只有 1 个任务时，整个流水线会被迫串行化，从而出现模型算力和线程池利用率很低的吞吐瓶颈，所以需要主动做“依赖松弛”；你项目中的策略是构图后检测首轮并发度，如果可执行任务过少就触发依赖降级函数，把并非强因果关系的依赖边从 hard dependency 降为 soft dependency 或直接移除（例如背景检索与并行事实补充这类可并发任务），再重算 `dependency_count` 和 ready 集合，以提升首轮并行数；风险控制则放在后续 Verify 与聚合阶段，通过结果一致性校验、关键字段补齐和冲突检测做补偿，避免并行提升后出现语义错序，这在业界属于典型“吞吐优先的 DAG 松弛策略”，关键是显式区分 hard/soft 依赖并保留完整审计日志，保证可追溯、可回滚、可解释。

### 7）项目中的状态快照恢复具体怎么做？
状态快照恢复的核心是把每次状态推进后的 `ResearchState` 按线程维度（`thread_id`）做 checkpoint 持久化，并允许在历史快照点进行回放与恢复执行，你项目基于 LangGraph checkpoint 机制（如 `MemorySaver`/`SqliteSaver`）配合线程级状态管理，在关键节点执行后保存可枚举快照，恢复流程是“列出 checkpoint → 选择目标 checkpoint → restore 到对应状态 → 从该节点继续调度”，如果再结合存储层的 `StateHistoryStore`（PostgreSQL）做历史归档，就能获得更稳健的长期追溯能力；这套能力在生产里价值很高，不只用于故障恢复，也可用于提示词/模型策略 A/B 调试、线上事故复盘、合规审计和可重复实验，等价于给 Agent 工作流提供“时间旅行 + 过程可重放”的工程底座。

### 8）质量门控怎么设计？常见指标有哪些？
质量门控的目标是判断“当前检索结果是否足以支撑高质量输出”，你项目目前已有三类硬指标：有效页面数量、正文长度、query 匹配率，即先判断有效文档量是否达阈值，再判正文信息密度是否足够，最后判语义匹配是否达标，任一不达标就触发补检索或爬虫兜底；在更完整的企业实践里，常扩展到来源多样性（域名分布）、时间新鲜度、重复率（正文哈希去重）、可引用性（是否可抽取证据片段）、冲突度（跨源结论一致性）和权限可见性，并将这些指标做成可配置阈值以适配不同行业场景（学术、金融、医疗等）；你当前“>5/6 门控通过率、平均 10 个有效页面”已经是不错结果型指标，下一步建议补充“门控失败后的补救成功率、补救成本、补救时延”三项闭环指标，这样才能完整衡量门控策略的工程收益而不仅是初筛效果。

### 9）JSON 标准输出控制如何详细实现？哪些设计负责保障稳定性？
JSON 标准输出控制通常采用“生成约束 + 结构校验 + 自动修复 + 失败降级”四层闭环，你项目已具备前两层主干能力：在 Prompt 层强约束输出 JSON 结构并定义字段模板，然后将返回映射到强类型契约（如 `TaskContract` 或 Pydantic 风格 schema）执行必填项、类型、枚举、长度、字段依赖关系校验；当校验失败时触发重试与 tier 升级，仍失败则走规则回退和默认模板，确保流程不断；若要进一步提升“标准格式可训练样本率”，可补一层业界常见 repair pipeline，对轻量语法错误（引号、逗号、尾随字符）进行语法修复，对缺失字段按规则补齐，对非法枚举做归一映射，再执行二次校验并生成 `validation_report`，最后仅允许“schema 合格 + 业务规则合格”的输出入库，这样能显著降低人工返工并提升线上稳定性。

### 10）详细讲讲存储层设计？项目是否具备高并发应对能力？
你的存储层属于典型分工式架构：PostgreSQL 承担事务与持久化（状态历史、迁移、任务日志、业务元数据），Redis 承担低延迟会话与事件流分发（例如 SSE 相关消息通道与短时状态），Qdrant 承担向量检索与语义记忆（task/document/summaries embedding），三者协同覆盖“强一致元数据 + 实时通信 + 语义召回”三类核心需求；就高并发能力而言，项目已经具备中等并发友好基础（异步接口、并发执行、缓存型中间层、可配置并发上限），但尚未完全演进到分布式高并发调度体系，因为 `ready_queue` 与调度闭环仍主要在单编排实例内，若并发继续提升，业界常见扩展路径是将任务分发外部化到消息队列（Redis Streams/Kafka）、引入任务幂等键与租约、给 PostgreSQL 增加连接池与读写分离、对 Qdrant 做分片与批量 upsert、对热点检索加缓存与限流，并在网关层配置熔断与退避重试，这样才能从“能并发运行”升级为“可水平扩展的生产级高并发系统”。

## 九、数学与代码表达补充（面试速记版）

### 1）Function Calling 的工具路由可用什么公式描述？
可以把工具选择抽象成一个带约束的排序问题，给定候选工具集合 $\mathcal{T}$，定义每个工具的综合打分
$$
S(t\mid q)=\alpha\cdot \mathrm{Rel}(q,t)+\beta\cdot \mathrm{Success}(t)-\gamma\cdot \mathrm{Cost}(t)-\delta\cdot \mathrm{Risk}(t)
$$
其中 $\mathrm{Rel}$ 是语义相关性，$\mathrm{Success}$ 是历史成功率，$\mathrm{Cost}$ 是时延/费用归一化，$\mathrm{Risk}$ 是失败或越权风险，最终选择
$$
t^*=\arg\max_{t\in\mathcal{T}} S(t\mid q)
$$
并受 schema 约束和权限约束共同过滤，这个表达在面试里能清晰体现你不是“拍脑袋选工具”，而是可解释的多目标路由。

### 2）RAG 检索与评估有哪些常用数学指标？
召回常用 Recall@k：
$$
\mathrm{Recall@k}=\frac{|\mathrm{Relevant}\cap\mathrm{TopK}|}{|\mathrm{Relevant}|}
$$
排序常用 MRR：
$$
\mathrm{MRR}=\frac{1}{N}\sum_{i=1}^{N}\frac{1}{\mathrm{rank}_i}
$$
增益质量常用 NDCG@k：
$$
\mathrm{NDCG@k}=\frac{\mathrm{DCG@k}}{\mathrm{IDCG@k}},\quad
\mathrm{DCG@k}=\sum_{j=1}^{k}\frac{2^{rel_j}-1}{\log_2(j+1)}
$$
在面试回答中你可以补一句“离线看 Recall/MRR/NDCG，在线看采纳率与追问率”，这就是完整评估闭环。

### 3）质量门控如何做成可计算规则？
可把门控写成加权分：
$$
Q=w_1\cdot f_{pages}+w_2\cdot f_{length}+w_3\cdot f_{match}+w_4\cdot f_{freshness}+w_5\cdot f_{diversity}
$$
当 $Q<\tau$ 时触发补检索/爬虫兜底；当 $Q\ge\tau$ 才进入生成阶段，这种“先证据后生成”的策略可显著降低幻觉和无依据回答。

### 4）上下文预算怎么量化？
给定总窗口上限 $B$（tokens），可分配为
$$
B=B_{sys}+B_{task}+B_{short}+B_{long}+B_{reserve}
$$
其中系统约束、任务指令、短期会话、长期记忆、保留冗余分别占预算；实际工程里可设动态策略，例如当检索证据变长时自动压缩历史对话摘要，保证关键证据优先进入窗口。

### 5）多 Agent 调度吞吐怎么表达？
在理想情况下，总吞吐近似
$$
\mathrm{Throughput}\approx \frac{\sum_i \mathrm{done\_tasks}_i}{T}
$$
首轮可并发任务数受 ready 队列大小约束：
$$
P_0=\min(|\mathrm{ready\_queue}|,\mathrm{max\_concurrency})
$$
因此依赖降级策略的核心就是提升早期 $|\mathrm{ready\_queue}|$，把串行链路转成可控并行链路。

### 7）拓扑调度可用最小代码怎么讲？
```python
from collections import deque, defaultdict

def topo_schedule(tasks, deps):
	indeg = {t: 0 for t in tasks}
	graph = defaultdict(list)
	for v, pres in deps.items():
		indeg[v] = len(pres)
		for u in pres:
			graph[u].append(v)

	q = deque([t for t in tasks if indeg[t] == 0])
	order = []
	while q:
		u = q.popleft()
		order.append(u)
		for v in graph[u]:
			indeg[v] -= 1
			if indeg[v] == 0:
				q.append(v)

	if len(order) != len(tasks):
		raise RuntimeError("cycle_or_deadlock")
	return order
```
这是 Kahn 算法的核心形态，面试时你可以补充“我们线上是增量版，不是一次性排完”，即可把算法和工程实现连接起来。

### 8）检索打分和重排的常见代码表达
```python
def hybrid_retrieve(query, dense_ret, sparse_ret, alpha=0.6):
	# 统一归一化后融合
	merged = {}
	for doc, s in dense_ret:
		merged.setdefault(doc, 0.0)
		merged[doc] += alpha * s
	for doc, s in sparse_ret:
		merged.setdefault(doc, 0.0)
		merged[doc] += (1 - alpha) * s
	return sorted(merged.items(), key=lambda x: x[1], reverse=True)
```
这段代码可以很直观地说明你理解“稠密检索 + 稀疏检索 + 融合重排”的主流 RAG 实践。
