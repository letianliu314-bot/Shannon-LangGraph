## Context

当前测试体系在“系统稳定性验证”“范式边界分类验证”“内容质量验证”之间耦合较高：
- 历史测试覆盖范围广但目标不聚焦，导致边界分类优化后难以清晰判断收益。
- Report / JSON 两类范式的判定、门槛、运行指标采集分散在不同脚本与结果格式中。
- 需要在不影响既有稳定性回归能力的前提下，对内容测试资产进行一次结构化重建。

约束与前提：
- 保留既有稳定性脚本（作为基线守护）。
- 删除不涉及稳定性与两类范式内容校验的测试文件。
- 后端执行为唯一计时口径（不含前端传输）。

## Goals / Non-Goals

**Goals:**
- 冻结首版指标与门槛定义，并形成单一事实来源。
- 建立双套 query 驱动测试：
  - Set A（20条）用于 report 范式。
  - Set B（5条）用于 json_train 范式。
- 统一测试执行与结果模型，逐条记录：
  - 分类结果（expected/observed）
  - 内容门槛结果
  - 运行指标（backend latency / parallel agent / token）
- 输出可比较、可追溯的汇总报告。

**Non-Goals:**
- 不在本变更中重构主业务编排逻辑。
- 不引入新的内容语义评分模型（JSON 暂无评分；Report 仅字数/引用临时评分）。
- 不引入前端端到端计时。

## Decisions

### Decision 1: 测试资产分层重组（稳定性层与内容层分离）
- 方案：将测试拆分为
  1) 稳定性保留层（原脚本原能力保留）
  2) 范式内容层（仅服务 report/json_train 边界与质量）
- 理由：避免单一脚本承担多个目标，提升失败归因清晰度。
- 备选方案：在原有测试上增量追加。
  - 放弃原因：会继续加重耦合，难以冻结统一口径。

### Decision 2: 分类判定与内容门槛采用“规则优先”
- 方案：通过 expected_mode vs observed_mode 计算分类准确率；内容以硬门槛判定通过/失败。
- 理由：规则可解释、可稳定回归，适合作为首版冻结基线。
- 备选方案：引入 LLM Judge 做统一判定。
  - 放弃原因：波动性更高，不适合当前冻结阶段。

### Decision 3: Report 与 JSON 采用差异化评价策略
- Report：门槛 + 临时评分（字数/引用）
- JSON：沿用结构校验，不设评分
- 理由：与当前业务目标一致，避免过早复杂化评分体系。
- 备选方案：两者都引入统一综合分。
  - 放弃原因：JSON 侧价值主要在结构合规，评分意义弱。

### Decision 4: 运行指标统一后端采集
- 指标：has_output、backend_latency_ms、parallel_agent_peak、token_used_once
- 理由：与用户要求一致，减少前端链路噪声。
- 备选方案：沿用前后端混合口径。
  - 放弃原因：不可比，且不符合当前约束。

### Decision 5: 统一结果数据模型与汇总产物
- 方案：每条 query 生成结构化记录，最终按 suite 聚合输出摘要。
- 理由：便于横向比较与后续自动化阈值治理。
- 备选方案：仅输出文本日志。
  - 放弃原因：难做统计与趋势分析。

## Risks / Trade-offs

- [风险] 删除历史测试可能误删隐性回归覆盖
  → Mitigation: 先按“保留稳定性脚本白名单”执行，删除前生成清单并复核。

- [风险] Report “引用合理性”仅用规则判定会有误判
  → Mitigation: 首版只做底线校验；后续再引入更强引用质量规则。

- [风险] backend latency 受运行环境波动影响较大
  → Mitigation: 汇总使用 P50/P90 与样本数，避免单点判断。

- [风险] token_used_once 口径可能包含估算值与真实值混用
  → Mitigation: 在结果字段中显式标记 token_source（estimated/actual）。

## Migration Plan

1. 固化 query 资产：将 Set A/Set B 作为测试输入基线文件。
2. 重组测试目录：保留稳定性脚本，清理非目标历史测试。
3. 建立统一执行入口：按 query 套件批量运行并写入逐条结果。
4. 落地门槛与评分逻辑：
   - Report: 500字、引用、流畅性门槛 + 字数/引用评分。
   - JSON: 结构与字段校验门槛。
5. 接入运行指标采集：后端时延、并行调度峰值、单次 token。
6. 产出 suite 级与总览报告，作为冻结基线。
7. 回滚策略：若新体系异常，恢复到稳定性脚本独立运行，并暂停内容层门槛判定发布。

## Open Questions

- token_used_once 若缺少真实 usage，是否允许 estimated 通过并在报告中降级标记？
