## Context

当前变更旨在把“内容是否可靠可用”从主观判断转为可重复、可审计、可回归的工程化测试能力。现状中，系统已具备多层架构、阶段门禁与验收脚本，但缺少针对输出内容质量的统一评测协议，导致以下问题：

- 结果可能形式合格但事实不可靠。
- 关键点覆盖缺失难以及时发现。
- 报告结构逻辑不稳定，影响协作复用。
- 面向最终用户的可执行性评估缺位。

约束条件与集成边界：
- 不破坏既有 append-only 治理策略。
- 与现有阶段门禁兼容，作为新增质量信号接入。
- 优先使用仓库内现有运行方式（脚本、测试、报告目录），降低迁移成本。

## Goals / Non-Goals

**Goals:**
- 建立四维内容质量评测框架：正确性、完整性、结构质量、可用性。
- 定义统一评分模型与判定阈值，形成通过/警告/失败结论。
- 产出标准化评测报告，支持审计与回归比较。
- 将评测结果接入阶段门禁，支持自动放行与阻断决策。
- 提供可复现样本集与基线结果，支持版本对比。

**Non-Goals:**
- 不在本阶段引入重量级在线评测平台。
- 不改变核心业务编排 DAG 的语义行为。
- 不将所有自然语言质量问题都做成模型训练问题。
- 不替代人工终审，仅提供结构化辅助决策。

## Decisions

### 1. 采用“四维评分 + 总分加权”作为统一判定模型

决策：
- 每条输出在四个维度产出子分数与问题清单。
- 使用可配置权重计算总分，并附加硬性门槛规则（例如正确性低于阈值直接失败）。

原因：
- 单一分数会掩盖关键风险，四维结构更利于定位问题。
- 允许按场景调整权重，同时保留质量底线。

备选方案：
- 仅输出通过/失败二值结论。未选原因：可解释性差，不利于持续改进。
- 全部依赖 LLM 主观评语。未选原因：稳定性与审计性不足。

### 2. 评测引擎采用“规则优先 + 可选模型辅助”

决策：
- 正确性和完整性先由规则与可验证证据驱动。
- 结构质量与可用性在规则基础上可引入模型辅助打分，但必须产出证据片段。

原因：
- 规则优先可保证可重复与可追踪。
- 模型辅助可以覆盖规则难以表达的语言质量特征。

备选方案：
- 纯规则。未选原因：对复杂表达的覆盖不足。
- 纯模型。未选原因：漂移风险高，复现性差。

### 3. 报告格式标准化为结构化文件

决策：
- 每次评测输出统一结构：输入摘要、四维得分、失败项、证据引用、建议动作、最终结论。
- 报告持久化到现有 reports 路径，便于与现有验收体系对齐。

原因：
- 结构化输出可被自动解析、聚合和回归比较。
- 与已有目录约定兼容，降低落地成本。

备选方案：
- 仅输出文本日志。未选原因：机器不可读，无法稳定比较。

### 4. 在阶段门禁引入“内容质量门”

决策：
- 将内容质量判定作为阶段门禁附加条件。
- 当质量结论为失败时阻断后续阶段；警告可按策略放行并记录风险。

原因：
- 门禁接入可把质量治理前置，减少低质量产物扩散。

备选方案：
- 仅离线报告，不参与门禁。未选原因：约束力不足。

### 5. 引入回归基线机制

决策：
- 维护固定评测样本与历史基线分。
- 每次变更执行对比，检测质量回退。

原因：
- 避免“单次看起来通过，但长期质量下滑”的问题。

备选方案：
- 不做基线，仅看当前分数。未选原因：无法检测回归。

## Risks / Trade-offs

- [风险] 维度权重设置不当导致误判 → 缓解：先采用保守默认权重，并通过历史样本校准。
- [风险] 模型辅助评分产生波动 → 缓解：关键维度以规则为主，模型输出需附证据并设置波动监控。
- [风险] 评测耗时上升影响迭代速度 → 缓解：分层执行（快速检查 + 深度检查），并支持只跑回归集。
- [风险] 样本集覆盖不足导致“测得过、线上差” → 缓解：建立样本补录流程，按问题类型持续扩充。
- [风险] 门禁过严影响交付效率 → 缓解：引入警告级别与人工豁免记录机制。

## Migration Plan

1. 新增内容质量评测脚本与评分配置，先以离线报告模式运行。
2. 建立初始样本集与基线分数，完成一次全量基线采集。
3. 将评测接入现有验收流程，但先以告警模式观察一轮。
4. 观测稳定后切换为门禁生效模式（失败阻断，警告留痕）。
5. 在 CI 或常用执行入口中加入回归评测步骤。

回滚策略：
- 通过开关关闭质量门禁，仅保留报告生成。
- 保留历史报告与基线文件，不删除评测产物，便于问题复盘。

## Open Questions

- 正确性维度的证据来源边界如何定义（仅输入上下文，还是可引入外部检索）？
- 四维默认权重在不同任务类型下是否需要预置模板？
- 警告级别的放行条件是否需要按 phase 区分？
- 是否需要为“可用性”增加角色化评估（如分析师、项目经理、工程师）？
